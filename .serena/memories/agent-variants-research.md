# Agent Variants Research Findings

## Current Status: Variants Still Active (Not Removed)

Despite a deprecation comment in the schema file, the full/slim variant system is **still in active use** throughout the codebase.

## 1. Agent Frontmatter: All Agents Declare "variant: full"

**Current implementation:**
- ALL 10 agents in framework modules declare `variant: full` in their markdown frontmatter
- Location: `framework/modules/*/agents/*.md`
- Agents: ai-framework-manager, ai-framework-developer, ai-backlog-manager, ai-architect, ai-app-developer, ai-ios-developer, ai-jira-manager, ai-confluence-manager, ai-book-writer, ai-report-manager
- All have `token-budget: 3000` (full agent budget)
- All have `delegates-to:` field (empty list - no actual delegation happening)

Example from ai-framework-manager.md:
```yaml
variant: full
delegates-to:
token-budget: 3000
```

## 2. Agent JSON vs Markdown Relationship

**File locations:**
- **Markdown source:** `framework/modules/*/agents/ai-*.md` (agent definitions, skill routing, context)
- **JSON derived files:** `.claude/agents/ai-*.json` (Claude Code custom agent definitions)
- **Commands (copies):** `.claude/commands/ai-*.md` (synced from module source)

**Relationship:**
- Markdown files are source of truth (contains variant field)
- JSON files are auto-generated from markdown via `AgentGenerator` class
- JSON files only generated for `variant: slim` agents (used for subagent invocation)
- Full agents have NO corresponding JSON files
- Commands are copies of markdown for backward compatibility

**AgentGenerator behavior:**
- Located in `framework/cli/src/lib/agent-generator.ts`
- Only generates JSON for `variant: slim` agents
- Full agents are not subagents, so they don't need JSON files
- When a slim agent exists, JSON is written to `framework/modules/{module}/agents/` then synced to `.claude/agents/`

## 3. Variants in Module.json and Registries

**Module.json:**
- Agents listed as simple string arrays (e.g., `"agents": ["ai-backlog-manager"]`)
- NO variant information in module.json structure itself
- Agent variant is determined by checking the markdown file frontmatter during build

**Schema files (agent.schema.ts):**
- Has deprecated variant enum exports (line 99-102)
- Actual AgentSchema does NOT include variant field (unified schema, not discriminated)
- Variant IS parsed from frontmatter via discovery engine during runtime

**Registry (agents.json):**
- Generated by registry-generator
- Includes `variant: "full" | "slim"` for each agent
- Used by validator and generator to understand agent types

## 4. Delegation Pattern: Fully Documented but Not Implemented

**Declaration:**
- All full agents have `delegates-to:` field in frontmatter (currently empty)
- Example: `ai-framework-manager.md` has `delegates-to:` with no values listed

**Validation (fully implemented):**
- `framework-validator.ts` has complete `validateAgentVariants()` method that:
  - Requires slim agents to have `parent-agent` field
  - Requires slim agents to have token-budget ≤ 1000
  - Requires slim agents to use only "basic" context level
  - Validates that full agents can only delegate to slim variants
  - Validates delegated agents actually exist and are marked slim

**Current state:**
- Validation rules are production-ready
- But NO slim agents actually exist in the codebase
- No delegation is actually happening (all agents are full)

**Mechanism:**
- Via Task tool (not automated)
- Full agent would invoke Task tool with slim agent ID
- Slim agent would execute with reduced token budget and context

## 5. Misleading Deprecation Comment

**The comment (line 99 in agent.schema.ts):**
```typescript
/** @deprecated No longer used - agent variants removed */
export const AgentVariantSchema = z.enum(["full", "slim"]);
```

**What this ACTUALLY means:**
- This specific schema export is deprecated (old dead code)
- The variant CONCEPT is NOT deprecated
- Variants are actively validated, stored, and used throughout the system
- Comment is misleading/wrong

**What's actually deprecated:**
- `FullAgent` and `SlimAgent` type names (now unified as `Agent` type)
- Not the variant field itself or the concept

## 8. Why Variants Exist vs Why They're Not Used

**Why variants system exists:**
1. Token budget management - slim agents for focused tasks (1000 vs 3000)
2. Context loading optimization - slim uses basic level only, full uses advanced/expert
3. Delegation pattern - full agents orchestrate, delegate focused work to slim
4. Cost reduction - lower token budgets and context for specialized tasks

**Why not used in practice:**
1. All agents default to full variant in templates
2. No slim agent examples created yet
3. Validation rules are ready but untested with real slim agents
4. Documentation is aspirational (shows what COULD be done)
5. Every agent ends up with 3000 tokens and advanced/expert context

## Key Insight

The slim/full variant system is **production-ready infrastructure** that's currently **unused**. It's like having plumbing installed but no water running through it. All the validation, generation, telemetry, and SDK support is there—it just needs someone to actually create a slim agent variant to test the system end-to-end.
