# Commit Message Standards

## Format

### With Jira Ticket
```
PROJ-123: Short descriptive title

- What was done (natural language)
- Another change made
- Additional work completed
```

### Without Jira Ticket
```
Short descriptive title

- What was done (natural language)
- Another change made
- Additional work completed
```

---

## Rules

### Title
- Short and descriptive (under 50 characters)
- Capitalize first word
- No period at end
- If Jira ticket in branch → prefix with `PROJ-123:`

### Body (Bullet Points)
- **3-7 bullet points** for most commits
- **Max 15** for large changes
- **Natural language** - write like a developer explaining to a colleague
- Start with what was done: "Added", "Fixed", "Created", "Updated", "Removed"
- No period at end of bullets
- No type prefixes (feat:, fix:) unless Jira ticket present

### What to Avoid
- Marketing buzzwords: "improvement", "enhancement", "optimize" (unless accurate)
- AI attribution: no "Generated by Claude", no "Co-Authored-By: Claude"
- Vague descriptions: "Fixed bug", "Updated code", "Made changes"
- Technical jargon when simpler words work

## Examples

### Good Examples

**With Jira ticket:**
```
DAPM-123: Add user authentication

- Created login form with email/password fields
- Added JWT token generation in auth service
- Wrote unit tests for login flow
- Fixed password validation for special characters
```

**Without Jira ticket:**
```
Add user authentication

- Created login form with email/password fields
- Added JWT token generation in auth service
- Wrote unit tests for login flow
- Fixed password validation for special characters
```

**Framework version update:**
```
[v1.2.0] Merge git workflow skills

- Combined jira-git-workflow into committing-code
- Added automatic Jira ticket detection from branch
- Simplified commit message format
- Updated all agent references
```

**Bug fix:**
```
DAPM-456: Fix login redirect loop

- Added check for existing session before redirect
- Cleared stale tokens on logout
- Added integration test for redirect scenario
```

### Bad Examples

```
Fixed stuff                           # Too vague
DAPM-123: Made improvements           # "improvements" is vague
feat: add login                       # Type prefix without Jira (should be plain)
Added new feature to improve UX       # "improve" is buzzword
Updated the code to be better         # What code? What's better?
```

---

## Multiple Tickets

When one commit addresses multiple tickets:
```
DAPM-123, DAPM-456: Refactor auth utilities

- Extracted token validation to shared module
- Updated both login and signup to use new module
- Added tests for edge cases
```

---

## Commit Size

- **Typical:** 5-30 lines changed
- **Large (acceptable):** Up to 100 lines for file reorganization
- **Too large:** Over 100 lines → consider splitting into multiple commits

Each commit should be a single logical change that could be understood on its own.

---

## Checklist Before Commit

- [ ] Title is clear and under 50 characters
- [ ] 3-7 bullet points describe what was done
- [ ] Natural language (no jargon, no buzzwords)
- [ ] Jira ticket included if branch has one
- [ ] No AI attribution lines
